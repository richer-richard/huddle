# huddle — future functionality brainstorm

## Executive summary

This document synthesizes six ideation lenses (messaging UX, security/privacy, files/media/calls, groups/rooms, identity/contacts, sync/ops/platform) into a single planning view. It is a planning artifact, not an implementation order, and nothing here is approved for build.

A few structural observations cut across every lens:

- **One foundational enabler gates a whole feature class.** Stable, sender-minted client message IDs (a random ULID inside the already-encrypted/signed body) are the cross-peer primary key for reactions, replies, edits, deletes, read markers, and reliable dedup of relay-redelivered messages. Several "obvious" features are blocked on it. It is the single highest-leverage low-risk item in the entire set.
- **huddle's honest-client + signed-envelope model already does most of the work.** Reactions, replies, edits/deletes, pins, roles, announcement channels, governance logs, and room metadata are all just new `RoomMessage` variants riding the existing `SignedRoomMessage`/Megolm path. The relay keeps seeing opaque blobs; the marginal cost is reducers + migrations, not new cryptography.
- **The biggest privacy wins are about metadata, not content.** Content is already E2EE. The frontier is what the relay (or a coerced operator) can still infer: the DM social graph (sealed sender), message size/timing (padding + cover traffic), reachability under censorship (obfuscated doors), and key-substitution MITM (safety-number change alerts). These advance the stated ethos most.
- **Several user-expected features deliberately strain the ethos and must be gated.** Read receipts, presence, link previews, voice/calls, handles, room directories, and federation all add metadata or attack surface. The responsible pattern recurs: off by default, opt-in, mutual/symmetric, coarse-grained, E2EE, and honestly framed in UX (never "deleted everywhere," never "guaranteed private").
- **Recovery and multi-device are the missing "survivable for humans" layer.** Today, losing a device means losing identity, rooms, and every hard-won verification. Encrypted local backup is a clean, low-risk first step; multi-device sync, social recovery, and personas are XL research bets that widen key-exposure blast radius and need explicit threat-modeling.

Privacy-posture flags are called out inline with **⚠ PRIVACY STRAIN** wherever an idea risks weakening metadata-minimization or adds attack surface.

### Quick wins (S effort, high value)

- **Markdown-lite formatting** — local render in egui RichText / ratatui spans; wire body stays literal source. ⚠ No previews.
- **Drag-drop + paste-image attach** — consume eframe `dropped_files` + `arboard` clipboard image into the existing `prepare_outgoing` path.
- **Contact nicknames + private notes** — finish the half-built `alias`/`note` UX; resolution order local alias > pinned profile name > anonymous.
- **Announcement / read-only channels** — `RoomKind::Announcement` + send/receive capability check; reuses owner-signer checks, no crypto.
- **Membership governance log** — persist a `room_events` table from already-verified signed control messages; pure local derivation, display only.
- **Screen-security toggles** — notification redaction under go-dark, blur-on-focus-loss in GUI, best-effort macOS window `sharingType=none`. ⚠ Screenshot prevention is best-effort; don't over-promise.
- **Diagnostics bundle (`doctor --bundle`)** — redacted logs + `PRAGMA integrity_check` + queue depths to a local file the user reviews before sharing. Observability without telemetry.

### Big bets / research (XL, or needs dedicated design)

- **Sealed-sender DMs & friend requests** — encrypt sender identity inside the payload; relay sees only a recipient-inbox hash, rate-limited via recipient-issued blinded delivery tokens. Arguably the single highest-leverage privacy win; abuse-resistance vs anonymity is the hard tension. Touches both hand-duplicated `ClientMsg`/`ServerMsg` copies.
- **Linked-device pairing + encrypted history sync** — second device under the same Ed25519 identity via SAS-gated, mailbox-wrapped seed transfer; chunked/resumable Megolm-session + history sync. ⚠ Widens key-exposure blast radius; sharing inbound Megolm sessions weakens forward secrecy as in any multi-device E2EE system.
- **Multiple personas (separate keypairs, one app)** — compartmentalized Work/Personal/Throwaway identities. ⚠ Cross-persona correlation (shared relay socket, Tor circuit, mDNS, reused avatar hash) is the whole game — must ship per-persona transport isolation, not just a name dropdown. Largest blast radius in the identity lens.
- **1:1 voice calls over the relay** — Opus frames sealed with the DM X25519 secret, relayed as opaque WS frames; no WebRTC (avoids ICE IP leak). ⚠ Relay now carries encrypted media volume/timing — a richer traffic-analysis signal than text. Gate to verified contacts; per-frame counter nonces mandatory.
- **Group voice/video via non-decrypting SFU fan-out** — relay forwards opaque per-sender Megolm-keyed frames. ⚠ Highest ethos strain in the set: relay sees participant set, per-sender timing/volume, and becomes a DoS-amplification target. Build only after 1:1 calls and forward-secrecy/rekey land; verified-rooms-only.
- **Relay-to-relay federation (signed room-id bridging)** — opt-in per room, owner-signed `FederationGrant`, relays gossip opaque blobs they can't decrypt. ⚠ Doubles the operators who observe a room's id/members/timing — opposite of metadata-minimizing. Heaviest item; sequence last; needs loop/replay dedup (message id helps).
- **Social recovery (Shamir-split friend shards)** — split identity-recovery secret k-of-n, E2EE to verified guardians over the mailbox. ⚠ A colluding/coerced threshold reconstructs your identity key — mandatory guardian re-verification on recovery + loud `SafetyNumberChanged` on recovered-to-new-key.
- **Username/handle system (self-certifying records)** — `{handle, pubkey, sig}` published to relay keyed by `hash(handle)`, verifiable offline; handle is a convenience pointer, never an authority. ⚠ Relay learns handle→key mappings (discoverability vs metadata-minimization tension); squatting/homoglyph risk — always show the fingerprint. Opt-in only.
- **Owner-curated room directory** — discovery as a signed `RoomInviteCard` feed inside an announcement-channel "hub" you opt into; no global crawlable index. ⚠ Opting into discoverability trades anonymity; relay sees hub-subscribe traffic. Curator-scoped, verified-only hubs.

## 1. Messaging UX

- **Stable client message IDs** *(prereq for everything below)* — sender-minted random ULID `client_msg_id` on every `RoomMessage`, persisted as an append-only column; travels inside the signed/encrypted body so the relay never sees it. Cross-peer primary key for reactions/replies/edits/deletes/receipts; also enables exactly-once dedup of mailbox-redelivered messages. **Must be random** (not a content hash) to avoid acting as a text fingerprint. *Effort M, risk low.*
- **Replies / quoting** — normal message carrying `reply_to: Option<client_msg_id>` plus a capped `quoted_excerpt` snapshot so the quote renders even if the parent was missed (offline-mailbox gap) or deleted. Render as "claims to quote," not verified provenance. *Effort M.* Depends on message IDs.
- **Reactions** — `Reaction { target_msg_id, emoji, op: Add|Remove }` variant inside `SignedRoomMessage` (Megolm-encrypted in encrypted rooms); per-peer `room_reactions` table, last-write-wins per (target, reactor, reaction) → a small CRDT set that converges under out-of-order/relayed delivery. Signed envelope binds reactor identity. Curated shortcode set + rate-limit to block spam and arbitrary-text exfil. *Effort M, risk med.*
- **Edit & unsend (tombstones)** — `EditMessage`/`DeleteMessage` applied only when signer fingerprint == original author (same check as `MemberLeave`/`ProfileUpdate`). Delete → tombstone + `deleted_at`; edit shows "(edited)". ⚠ **Best-effort "unsend among honest clients," NOT secure deletion** — a modified client or already-delivered mailbox copy can ignore it; UX must say "removed for people using huddle." *Effort M, risk med-high.*
- **Markdown-lite formatting** — deterministic subset (bold/italic/strike/inline+fenced code/blockquote), rendered locally; wire body stays literal source, so no protocol change. ⚠ **Hard-exclude auto-fetched link/image previews** (a de-anon + read-receipt beacon out of Tor); links inert text only; sanitize so formatting can't spoof UI chrome (fake "verified" badges). *Effort S.* Pairs with code-block copy buttons.
- **Drafts + offline-aware queued/scheduled send** — per-room drafts persisted locally; a local "send when online" queue flushes when `room_send_readiness` reports a door reconnect; time-based scheduling is local-only (message held on-device, never parked on the relay — that would leak send-time intent). ⚠ Queued bodies inherit existing plaintext-at-rest exposure under `--no-master-passphrase`. *Effort M.* (Overlaps the sync-lens **offline outbox**; unify.)
- **Mentions → addressable autocompleted pings** — upgrade substring `MentionReceived` to `@`-autocomplete from the member list, storing mentions as **fingerprint-anchored** spans (immune to rename-spoofing), rendered as current display name; adds a Mentions filter + unread badge. Local resolution against `peer_profiles`/contacts. *Effort M, risk low.*
- **Pinned messages** — `PinMessage { target_msg_id, op }` accepted only from a current owner (same authz as `OwnerGrant`/`BanMember`); `room_pins` table → collapsible "Pinned" strip. Keeps a room's invite code/rules/meeting link reachable. *Effort M.* Depends on message IDs.
- **Voice messages as encrypted attachments** — short Opus clip through the **existing** `FileOffer`/`FileChunk` pipeline (mime `audio/opus`, `duration_ms` hint), rendered as inline player + waveform. No new transport crypto — inherits Megolm-wrapped file keys + SHA-256. ⚠ Adds mic-capture permission + audio codec attack surface and biometric/voiceprint content; default to manual playback, respect go-dark, strip device metadata, gate behind opt-in flag. *Effort L.* (Duplicated in the files lens — merge.)
- **Tasteful read & delivery state** — two layers. **(1)** Local delivery confidence ("sent / queued / delivered to relay") derived purely client-side from `room_send_readiness` + mailbox ack, **no recipient signal** — pure win. **(2)** ⚠ **PRIVACY STRAIN:** optional mutual read receipts — only if **both** peers opt in does each send a signed, debounced `ReadUpTo { client_msg_id }` watermark inside the envelope. Default OFF, symmetric (can't see others' reads without exposing your own), coarse (read-up-to, not per-message timestamps). *Effort M.* (Same feature appears in the sync lens — single design.)

## 2. Security & privacy

- **Disappearing messages (signed per-conversation TTL)** — off/1h/1d/1w in `app_settings` + `rooms`; a signed `RetentionPolicy` variant propagates the owner's choice attributably, outgoing messages embed optional `expires_at_ms`; a background sweep (mirroring the friend-request TTL sweep + server mailbox GC) deletes expired rows; undelivered ephemerals also self-destruct server-side via `MAILBOX_TTL_SECS`. ⚠ Honest-client-enforced, not cryptographic. Sweep must run inside the global Mutex without holding the lock across await. *Effort M.* Complements the plaintext-at-rest weakness directly.
- **Panic / duress wipe with decoy passphrase** — two unlock slots: the real one derives the true master key; a duress passphrase opens a decoy DB or triggers irreversible secure-delete of DB + identity secret + `keychain.salt`. Because SQLCipher derivation is passphrase-driven, a duress entry is cryptographically indistinguishable from a typo (no decoy oracle). Hidden hotkey for instant wipe-and-quit. ⚠ Plausible deniability is hard to fully achieve (FS timestamps, relay mailbox state, SSD secure-delete limits) — conservative UX claims required. *Effort L.* Flagship for the target threat model.
- **Encrypted, shardable identity & key backup (recovery kit)** — export identity secret + room/DM session pickles + contacts under a fresh Argon2id key from a recovery passphrase; two modes: self-stored passphrase file, or optional Shamir 2-of-3 split. Import re-keys the DB and re-installs Megolm inbound sessions so history decrypts again. ⚠ A backup is a copy of long-term secrets — weak passphrase = weakest link; never touches the relay; Megolm outbound restore must avoid ratchet/nonce reuse. *Effort L.* (Overlaps the sync-lens local backup + identity-lens address-book backup + social recovery — consolidate into one recovery-kit design.)
- **⚠ Sealed-sender DMs & friend requests** — today `SendDirect` carries a cleartext recipient `to` and a sender-authenticating `Hello`, so the relay can build a sender→recipient edge for every DM. Encrypt the sender's identity+signature **inside** the payload (under the recipient's inbox key); decouple send-authorization from inner identity via a per-recipient blinded/rotating delivery token so the relay rate-limits without learning who talks to whom. **Highest-leverage privacy win**, but abuse-resistance vs anonymity is a genuine tension and the token design is subtle; timing/size correlation can still leak. *Effort XL.* Touches both `ClientMsg`/`ServerMsg` copies.
- **⚠ Traffic-analysis resistance** — **(1)** pad outbound blobs to fixed buckets (256B/1KB/4KB) before publish/`SendDirect` so a one-word reply isn't distinguishable from a key rotation by length. **(2)** optional steady-state cover traffic: padded dummy frames to the user's own inbox on a jittered schedule. Both pure client-side above the door abstraction; relay still sees opaque blobs. Cover traffic costs bandwidth/battery, can be fingerprinted by regularity (needs jitter), default off; real protection vs a global passive adversary is limited — be honest. *Effort M.*
- **Pluggable obfuscated transport door** — a sixth `TransportId` wrapping the relay WS in obfs4/meek-style pluggable transports and/or domain-fronted wss, slotting into the existing most-private-first door ordering as a fallback when onion/clearnet doors are blocked. ⚠ PT bridges/fronting endpoints need provisioning and get enumerated/blocked over time; domain fronting is increasingly unsupported by major CDNs; adds external proxy deps; misconfig could fail open to a detectable transport. *Effort L.* Pure anti-censorship; fits the doors model exactly.
- **Per-conversation verification UX (safety numbers + change alerts + badges)** — surface the existing TOFU pins + `verified_peers`/SAS as always-visible per-conversation state: a deterministic Signal-style safety number in each header with tap-to-verify (QR/SAS), and a **loud in-thread `IdentityKeyChanged` event when a pinned Ed25519 pubkey changes** — block sending until re-verify or explicit accept. ⚠ Alert fatigue is the main risk: must distinguish expected rotation (forward-secrecy roadmap, self-signed by the old key) from an unexplained swap. No new crypto. *Effort M.* (Identical to the identity-lens **safety-number alerts** — one feature.)
- **Screen-security hardening (local-only)** — notification redaction ("New message" under go-dark/privacy flag), blur-on-focus-loss / screen-share overlay in the GUI, best-effort screenshot/recording deterrence (macOS window `sharingType=none`). ⚠ Screenshot prevention is best-effort and platform-dependent — don't over-promise; blur/redaction are robust. *Effort S.*
- **Tamper-evident local message log (hash-chained audit)** — each stored row gets a `prev_hash` over (sender_fp + body + sent_at) with a separately persisted head hash; load-time verification detects out-of-band deletion/edits. Optional signed `LogCheckpoint` lets two peers exchange head hashes to detect a forked/truncated history view — a lightweight transparency check with no central log. ⚠ Checkpoint comparison needs tolerance windows for legitimate late/out-of-order delivery (false-positive risk); detects, never prevents. *Effort M.*

## 3. Files, media & calls

- **Inline image/video thumbnails** — render decrypted images as egui textures + video poster frames instead of generic cards. Sender generates a small (~256px) thumb, encrypted under the **same** per-file ChaCha20-Poly1305 scheme (fresh key, Megolm/ECDH-wrapped, content-hash AAD), shipped as an optional `thumb_b64` on `FileOffer`; receiver decrypts on offer arrival (no chunk wait) with a blur-up placeholder. ⚠ Thumbnails are decoded image data — hardened/pure-Rust decoder, bounded dimensions, strict byte cap; strip EXIF on generation. TUI degrades to dimensions+size (or sixel/kitty behind a flag). *Effort M.*
- **Large-file & resumable transfer (libp2p stream protocol)** — lift the 1 MiB cap: keep `FileOffer` on gossipsub but move bulk bytes onto a request-response `/huddle/file/1` stream dialed to the sender, falling back to relay-circuit. Resumability is nearly free — `accept_chunk` already keys chunks by index and writes `.part`, so a missing-index bitmap on reconnect re-streams only the gaps; final SHA-256 unchanged. ⚠ New network surface — reuse the existing per-chunk caps (index bound, `data.len` bound, running-bytes ceiling) to prevent heap-exhaustion DoS; `.part` files widen at-rest exposure window → needs cache-GC. Direct dial can reveal a dialable address (mitigated over Tor/relay-circuit). *Effort L.*
- **Voice notes (push-to-record Opus)** — *(merges with the messaging-lens voice messages — single feature)* capture via cpal, encode via audiopus/opus, run through `prepare_outgoing_from_bytes` + `encrypt_file`, send as `FileOffer`/`FileChunk` (mime `audio/ogg`), with `duration_ms` + a small peak-array for the waveform. Reaches offline contacts via the mailbox. ⚠ Mic capture is a sensitive native capability (explicit push-to-talk, visible recording indicator, no background capture); libopus is C (sender-side memory-safety surface); voice is biometric content. *Effort M.*
- **Drag-and-drop + paste-image-from-clipboard** — front-end only on the existing attach method: consume eframe `dropped_files`; read clipboard image via `arboard` on Ctrl/Cmd-V → temp PNG → same `prepare_outgoing` path; auto-name `pasted-<date>.png`. Reuse `sanitize_filename` + size cap. *Effort S, risk very low.*
- **⚠ Privacy-preserving link previews (sender-only fetch)** — solve the classic "N recipients ping a tracker" leak by having **only the sender** fetch (over the active door, i.e. through Tor when selected), extract title/desc/og:image, downscale, strip tracking params, and embed the preview as an **encrypted attachment-like payload**; recipients render from E2EE data and never make an outbound request. Off by default, per-link opt-in, with a "this fetched from your machine" indicator. ⚠ Still a net-new outbound-request capability — one fetch leaks the sender's interest in a URL; hardened sandboxed HTML extractor, cap redirects, no JS, allowlist image types, **block private IP ranges (SSRF)**. The single biggest ethos strain in this lens. *Effort M.*
- **Self-hosted sticker/emoji packs (E2EE, no CDN)** — a pack is a manifest + small WebP/APNG images distributed over the existing file path; each sticker content-addressed by SHA-256 and cached, so a popular sticker is sent once then becomes a tiny by-reference `file_id` message (full chunks only on cache-miss). Replaces the Giphy/Tenor CDN-tracking model entirely; dedup-by-hash is a free efficiency win. ⚠ Animated formats add decoder surface — bound frame count/dimensions; by-reference cache-miss must fall back to a full offer, not a broken render. *Effort M.*
- **Progressive media preview (streaming while chunks arrive)** — expose an in-order-prefix read on `FileManager` so the GUI starts decoding audio/video on a contiguous head rather than blocking on final SHA-256. ⚠ Plays bytes before whole-file verification — mitigate by only progressive-playing **encrypted** transfers (each chunk is AEAD-protected, so per-chunk integrity holds), marking playback "verifying…", and never exposing/saving the prefix as trusted until the final hash matches; decoder must tolerate truncation. *Effort L.*
- **⚠ 1:1 voice calls over the relay** — no WebRTC/STUN/TURN. Signaling (invite/accept/decline/hangup) rides the DM channel as signed `RoomMessage` variants; media is 20ms Opus frames sealed with the DM X25519-ECDH secret under ChaCha20-Poly1305 (per-frame counter nonce), relayed as opaque WS frames; jitter buffer + Opus FEC absorb Tor latency. More private than WebRTC (which leaks both IPs via ICE). ⚠ Relay becomes a per-stream forwarder seeing encrypted media volume/timing ("a call is happening") and doubles per-call bandwidth — a richer traffic-analysis signal than text. Gate to verified contacts; document the tradeoff. *Effort XL.*
- **⚠ Group voice/video via non-decrypting SFU fan-out** — optional relay role that forwards opaque per-sender frames (encrypted under a dedicated per-call sender key, rotated like the room key) without decrypting; active-speaker + join/leave reuse signed variants. The only realistic topology over high-latency Tor (full-mesh melts). ⚠ **Highest ethos strain:** relay sees stream timing, per-sender volume, and the participant set, and becomes a DoS-amplification target (one sender → N forwards); per-call rekey-on-membership-change must be airtight. Strictly opt-in, verified-rooms-only; **build only after 1:1 calls + forward-secrecy/rekey land.** *Effort XL.*

## 4. Groups & rooms

- **Tiered role/permission matrix** — generalize the `owner`/`member` role column into owner > moderator > member > muted/read-only via a signed `RoleGrant { target_fp, role }` (generalizes `OwnerGrant`); honest clients apply only if the signer outranks the grant; roles ride in `RoomAnnouncement` so newcomers learn the mod set like they learn owners. ⚠ Soft enforcement — a patched client can ignore caps; true silencing of a muted member still needs a key rotation excluding them; role state can diverge briefly during partition. *Effort M.* No new crypto.
- **Multi-use, expiring, revocable invite codes (with ledger)** — replace the in-memory single-use 10-min code with a persisted `room_invite_codes` table (store **only a hash** of the code), owner-chosen TTL + max-uses, `revoke_join_code`, and a live-codes list; `CodeJoinRequest` checks the ledger instead of the volatile vec. ⚠ A leaked-but-unrevoked code is usable until expiry — mitigated by max-uses + revocation; hashing avoids DB-theft leakage. *Effort M.* Builds on the Phase F code-join flow.
- **Announcement / read-only channels** — `RoomKind::Announcement` (`serde(default)` back-compat) where honest clients reject any `Plain`/`Encrypted` post whose signer isn't owner/mod; composer hidden for everyone else. Pair with client-side slow-mode (min seconds between a fingerprint's posts). ⚠ Honest-client enforcement — a patched client can still publish to the topic; receivers just drop it. *Effort S.* Newsletters/release-notes/town-square without a different tool.
- **Room topic, avatar, pinned-rules (signed metadata)** — `RoomMetaUpdate { topic, avatar_blurhash_or_small_png, rules, updated_at }` inside `WireMessage::Signed`, owner-only, last-write-wins (mirrors `ProfileUpdate`); for encrypted rooms encrypt the meta blob under the current Megolm key so the relay never sees it; cap avatar to a few KB or blurhash+thumbnail. ⚠ Avatar bytes are attacker-controlled input rendered in two GUIs — size-cap + defensive decode (image-bomb); default to encrypting so unencrypted rooms don't leak topic/avatar to the relay. *Effort M.*
- **Forward-secure member removal (auto-rekey on kick/leave)** — wire `BanMember`/remove to automatically trigger the existing `rotate_room`: acting owner mints a fresh outbound Megolm session and re-wraps it (via `MemberAnnounce`/`CodeJoinResponse`-style ECDH) to remaining members only, excluding the removed fingerprint — making rekey the default of kick, not a manual step. ⚠ Highest-value, trickiest: rekey must reach every remaining member or honest clients fragment into old/new-key cohorts (a member who misses the rotation goes silently read-only); concurrent membership changes need careful sequencing. *Effort L.* **Design jointly with `docs/ROADMAP-forward-secrecy-and-rekey.md` §1.**
- **⚠ Owner-curated room directory (signed, opt-in)** — no server-hosted index: an owner publishes a signed `RoomInviteCard` (id, name, topic, avatar, verified_only flag, join code) shareable as paste/QR; a "community hub" is itself a room whose announcement channel carries a feed of these cards, so joining the hub = subscribing to a directory. ⚠ Public-by-design rooms invite spam and make room existence + membership-interest observable to the relay (hub-subscribe traffic); only as trustworthy as the curator. Keep strictly opt-in + curator-scoped + verified-only hubs, never a global crawlable index. *Effort L.*
- **Membership audit log + ban/role event feed** — persist a `room_events` table from already-signed control messages (`OwnerGrant`/`RoleGrant`/`BanMember`/`MemberLeave`/joins) as a per-room "governance log" so members see who banned/promoted whom; each entry carries a verified signer fingerprint, unforgeable by the relay or non-owners. ⚠ Members who were offline may hold slightly different logs (eventual-consistency gap) — UI should signal incompleteness rather than imply a complete record. *Effort S.*
- **Member capacity guardrails + large-room health UI** — owner-set soft `max_members` cap (honest-client-enforced on `MemberAnnounce`, mirroring the existing 2-member Direct cap) plus a room-health panel (member count, inbound Megolm sessions held, queued/dropped indicators) and backpressure (coalesce typing indicators, batch `FileChunk` fan-out under bursts). ⚠ Cap is honest-client-only; metrics are local. Backpressure on typing actually reduces metadata volume. *Effort M.*
- **⚠ Relay-to-relay federation (signed room-id bridging)** — opt-in per room: an owner's signed `FederationGrant` authorizes relay A to bridge a room id to relay B; relays gossip the same opaque cleartext-id blobs to each other (still never decrypt); clients unchanged. ⚠ Largest blast radius: now **two** operators observe a room's id, member fingerprints, timing, and volume (opposite of metadata-minimizing); needs relay-loop/replay dedup (message id helps) and authorization so a malicious relay can't silently subscribe rooms it wasn't invited to. Strictly opt-in with clear UX that bridging exposes the room to a second operator. *Effort XL.* Sequence last; touches both `ClientMsg`/`ServerMsg` copies + a new inter-relay protocol.

## 5. Identity & contacts

- **Signed rich profile cards (avatar + bio + status)** — extend `ProfileUpdate` to a versioned blob: display name, status line, short bio, avatar referenced by `avatar_sha256` (+ blurhash for instant render); text rides the existing signed envelope (last-write-wins), avatar fetched lazily over the encrypted file path, **never embedded inline** so announce payloads stay small. New `peer_profiles` columns (append-only). ⚠ Avatars are attacker-controlled bytes — strict size/dimension caps, panic-safe decode, strip metadata; render fingerprint/safety-code alongside the name (never let a display name stand alone as identity); richer profiles are more cross-room fingerprintable (per-persona mitigation). *Effort L.* `widgets/avatar.rs` is a placeholder to flesh out.
- **Safety-number / pubkey-change alerts** — *(same feature as security-lens verification UX — single design)* promote the existing silent drop on pubkey mismatch into a first-class `SafetyNumberChanged` event + banner driven by a global `pinned_keys(fingerprint, pubkey, pinned_at)` table; DM stays usable but unverified until re-SAS. ⚠ Distinguish self-announced rotation (signed by the **old** key — forward-secrecy roadmap) from an unexplained swap; only alarm loudly on the latter. *Effort M.* The single most important anti-MITM affordance, and the data already exists.
- **Contact nicknames + private notes** — finish the half-built `alias`/`note` UX: local-only nickname overriding self-asserted display name everywhere, plus a freeform note ("verified in person 2026-05"); resolution order local alias > pinned profile name > anonymous (an anti-spoof property in itself); included in the encrypted address-book backup, never broadcast. ⚠ Notes are plaintext-at-rest like the whole DB — "private" = "as private as the master passphrase"; never log/broadcast. *Effort S.*
- **⚠ Multiple personas (separate keypairs, shared app)** — generalize the single-row `identity` table to N keypairs (Work/Personal/Throwaway), each its own Ed25519 identity, DM key, profile, and contact set; `persona_id` FK across rooms/contacts (back-fill to persona 1). ⚠ **Personas must be cryptographically unlinkable on the wire** — cross-persona correlation is trivially introduced via a shared relay socket, reused Tor circuit, mDNS on the same LAN, or a reused avatar hash; requires per-persona transport isolation + storage isolation + clear UI to prevent posting from the wrong persona. Largest blast radius in this lens; ship per-persona-circuits, not just a name dropdown. *Effort XL.*
- **⚠ Username/handle system (self-certifying records)** — a signed `{handle, ed25519_pubkey, claimed_at, sig}` published to the relay keyed by `hash(handle)`, verifiable offline; first-claim-wins per relay with explicit collision display; the handle is a convenience pointer, the fingerprint/safety-code remains the real anchor; a handle resolving to a new key fires `SafetyNumberChanged`. ⚠ Handle-squatting + homoglyph impersonation — normalize/confusable-check, always show the fingerprint, never let a handle alone establish trust; the relay learns handle→key mappings (metadata surface) — keep signed-but-not-required and per-relay, not a global namespace; opt-in (no handle = zero discoverability). *Effort L.*
- **Encrypted address-book backup + restore** — export contacts (alias, note, pinned pubkey, dm_room_id, source) + `verified_peers` + pinned safety numbers as one passphrase-encrypted bundle (Argon2id + existing ChaCha20-Poly1305); restore merges by fingerprint, preserving manual verifications and notes, **without** moving the identity secret (separate, more sensitive op). ⚠ The bundle is a concentrated trust-graph artifact — encrypt strongly, warn it reveals the whole social graph if the passphrase leaks; restore must re-validate each pinned pubkey still derives its claimed fingerprint. *Effort M.* (Consolidate with the security/sync recovery-kit work.)
- **QR / NFC quick-add with embedded safety code + auto-verify** — a dedicated **contact** QR/NFC payload encoding `{fingerprint, ed25519_pubkey, optional handle, optional relay_url}` as a signed blob (distinct from a room invite); scanning in person both adds **and** auto-marks verified (in-person scan IS the SAS comparison); the screen confirms the derived fingerprint + SAFE-XXXX so a tampered QR is visibly wrong. ⚠ QR/NFC are attacker-influenceable captured input — show the pubkey + confirm the derived code before auto-verify; treat NFC identically to QR. *Effort M.* Makes strong verification the default path, not a chore.
- **⚠ Private presence (opt-in, contact-scoped, signed heartbeats)** — *(pairs with the manual status line above)* instead of relay-tracked online/offline, a low-frequency signed "alive" heartbeat E2EE-delivered **only** to explicitly chosen contacts via their DM inbox — coarse ("active in last hour," never precise timestamps), default-off, per-contact revocable; the relay sees only an opaque DM blob and learns no presence semantics. ⚠ Any presence is a metadata cost even to chosen contacts — bucket coarsely to avoid sleep-pattern/timezone profiling; strictly opt-in. *Effort M.*
- **⚠ Social recovery (Shamir-split friend shards)** — split an identity-recovery secret k-of-n (e.g. 3-of-5), E2EE each shard to chosen verified guardians over the DM/mailbox path; recover by requesting a threshold of shards back to a fresh keypair, reconstructing the original secret locally. ⚠ Highest-sensitivity: a colluding/coerced threshold reconstructs your identity key — guardian selection, recovery-request authentication, and replay/impersonation defenses are critical; **require guardians to re-verify the requester before releasing a shard**, rate-limit/notify on attempts, and fire a loud `SafetyNumberChanged` on recovered-to-a-new-key. *Effort XL.* (Unify with the encrypted recovery-kit family.)

## 6. Sync, ops & platform

- **Linked-device pairing (per-device subkey under one identity)** — pair over SAS: fresh per-device X25519 ephemeral, run the shipped SAS flow out-of-band, primary wraps and transfers the identity secret + Argon2id material through the per-fingerprint mailbox as opaque ciphertext; record each device's libp2p PeerId in a `linked_devices` table. The huddle-1.2 `Deliver`-to-fingerprint path already fans out to all live connections, so the relay needs no change. ⚠ Seed transfer is the crown-jewel op — SAS-gated + mailbox-wrapped or a pairing MITM = full account takeover; one shared Ed25519 key means any device compromise compromises the identity (no per-device revocation without a deeper key hierarchy); relay observes one fingerprint now has multiple PeerIds (metadata signal). *Effort L.*
- **⚠ Encrypted history sync to a linked device** — after pairing, export room/DM Megolm session pickles + contacts + recent history under an HKDF-from-SAS sync key, chunk + ack + resume through the bounded/TTL mailbox, importer replays into `repo::insert_*` and `add_inbound_session` so past room history decrypts on the new device. ⚠ Moves decrypted history + inbound Megolm sessions between devices — weakens forward secrecy as in any multi-device E2EE system and materially increases single-device-compromise blast radius; partial-transfer states need careful resume against the TTL mailbox. *Effort XL.* Depends on device pairing.
- **Passphrase-wrapped local backup/restore (`huddle backup`/`restore`)** — one self-contained archive (SQLCipher DB + `identity.key` + `keychain.salt` + Megolm pickles) re-encrypted under a **new** backup passphrase (independent Argon2id, its own salt in the header); offline + file-based via the shipped rfd dialogs, **never uploaded**. ⚠ The archive is the entire account in one file — must NOT reuse the login salt, warn it's as sensitive as the seed, refuse obviously-synced folders without confirmation. *Effort M.* The privacy-first answer to "where's my backup?" precisely because it doesn't phone home. (Anchor the consolidated recovery-kit design here.)
- **Offline outbox (persisted send-queue + exponential backoff)** — persist every unconfirmed composed message into an `outbox` table (id, target, ciphertext, attempts, next_retry_at); a background task drains it when a door comes up, retrying most-private-first, removing a row only on the relay's `Sent { delivered, queued }` ack; replays on crash/restart. Complements the **server-side** mailbox (recipient offline) by handling the **sender** offline/mid-flap. ⚠ Idempotency via message id; needs max-attempts/TTL cap mirroring `MAILBOX_TTL` so the table doesn't grow for a permanently-gone recipient. *Effort M.* (Unify with the messaging-lens drafts/queued-send.)
- **⚠ Metadata-light delivery + read receipts (opt-in)** — *(same feature as messaging-lens read state — single design)* tiny signed `Delivered{msg_id}` / `Read{up_to_msg_id}` envelopes over the encrypted DM/room channel (never a server feature), coalesced one-per-flush, per-conversation opt-in, default off for unverified contacts; surfaced via `ReceiptUpdated`. ⚠ Read receipts reveal presence/reading habits to the peer — make "off" the default, never send to blocked/unverified peers; relay learns nothing beyond timing it already sees. *Effort M.*
- **Reproducible cross-platform packaging** — GitHub Actions matrix building huddle-gui + TUI for Linux x86_64/aarch64 (AppImage + .deb) and Windows (signed MSI + portable .zip), with checksums and ideally reproducible builds; statically bundle Arti so there's no system-Tor dependency; mirror the macOS `huddle app` flow. ⚠ Supply-chain integrity is the whole point — reproducible builds + published checksums + code signing where feasible; keep libp2p 0.56 pinned identically across crates or cross-builds drift. *Effort L.* Widens reach for a censorship tool where Windows/Linux desktop is a core audience.
- **Privacy-preserving diagnostics bundle (`doctor --bundle`)** — extend the shipped `doctor` dump into an opt-in export: redacted logs + transport/door connectivity + `PRAGMA integrity_check` + schema `user_version` + mailbox/outbox queue depths to a local file; redact fingerprints/IPs/room ids by default; **never auto-sent** — the user reviews before sharing. *Effort S.* Observability without telemetry; a differentiator.
- **Large-history performance (virtualized render + keyset pagination)** — replace full-history loads with keyset-paginated reads (`WHERE id < cursor ORDER BY id DESC LIMIT N`) on a `(room_id, id)` index; virtualize the TUI/GUI list so only the visible window renders; lazy-load older pages on scroll. ⚠ The real hazard is lock discipline — keep DB work synchronous and short (holding the single `Arc<Mutex<Connection>>` across an await poisons it). No crypto/network surface. *Effort M.*
- **⚠ Background auto-update with signed manifests** — periodically fetch a small Ed25519-signed release manifest (version, per-platform hashes, URLs) **over a transport door** (prefer onion/relay so checks don't deanonymize via a clearnet CDN hit), verify against a baked-in maintainer key, verify the hash, stage the swap (delegating to OS package managers where they own the binary); user-gated prompt, not silent. ⚠ A high-value supply-chain target — pinned maintainer keys + signature verification non-negotiable; a naive clearnet check leaks "this IP runs huddle" + version (fingerprinting/targeting). Done wrong it badly strains the ethos. *Effort L.* Depends on the packaging + signing work; critical so security fixes (e.g. the recent rustls CryptoProvider fix) actually reach stale `cargo install` users.

## Cross-cutting notes

- **Consolidate the recovery family.** Encrypted identity/key backup (security), passphrase-wrapped local archive (ops), encrypted address-book backup (identity), and Shamir social recovery (identity/security) overlap heavily. Design one recovery-kit module with clear tiers: address-book-only (low sensitivity) → full local archive (high) → social/Shamir (highest), sharing the Argon2id + ChaCha20-Poly1305 primitives.
- **Consolidate receipts/presence.** Read receipts appear in two lenses and presence in one — one signed-watermark design, mutual + coarse + opt-in + E2EE, covers all three.
- **Consolidate verification alerts.** Safety-number change alerts appear in both security and identity lenses — one `SafetyNumberChanged`/`IdentityKeyChanged` event + `pinned_keys` table.
- **Coordinate every rekey-adjacent item with the forward-secrecy roadmap.** Forward-secure member removal, multi-device Megolm sharing, per-call sender keys, and the "expected rotation vs unexplained swap" distinction in safety-number alerts all touch `docs/ROADMAP-forward-secrecy-and-rekey.md`. Design together to avoid divergent key-rotation semantics.
- **The honest-framing rule is load-bearing.** Edit/unsend, disappearing messages, duress wipe/deniability, screenshot prevention, and cover traffic all offer guarantees that are soft or best-effort. Every one must say so in UX — overpromising "deleted everywhere" / "undetectable" / "guaranteed private" would betray the project's trust model more than shipping nothing.
